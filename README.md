# splicertc

TCP/TLS-туннель для сетей, где режется UDP и большинство портов, но
проходит TLS на почтовых портах (587, 993). Главный режим `vpn` заворачивает
весь IPv4-трафик Windows-машины в TLS до своего VPS. UDP игр при этом идёт
отдельным каналом: каждый пакет копией по 2–3 параллельным соединениям,
сервер берёт первую дошедшую копию. Так одна потеря в TCP не задерживает
игровые пакеты.

## Как устроено

| Канал | Порт по умолчанию | Что везёт |
|---|---|---|
| vpn | `:8447` (в примере `:587`) | целые IPv4-пакеты; на сервере TUN + NAT |
| glue | `:8446` | UDP игр, мультипас с дедупликацией |
| reliable | `:8443` | TCP-соединения локального SOCKS5-прокси (smux) |
| droppable | выключен | тестовые кадры для замеров потерь, только лог |

Любой канал выключается значением `"off"`. Каждое соединение: TLS 1.3,
сервер проверяется по отпечатку сертификата (пин), клиент по ключу
Ed25519. Внутри туннеля своя очередь FQ-CoDel: мелкие пакеты (игра, DNS,
ACK) уходят раньше загрузок.

Компоненты: `cmd/server` (VPS, Docker), `cmd/client` (Windows),
`cmd/tray` (GUI для `vpn`), `cmd/genkey`, `cmd/gencert`, `cmd/portprobe`
(какие порты пропускает сеть), `cmd/tunprobe` (что видит TUN).

## Установка

### 1. Ключ

Ключ генерирует сам клиент, и приватная часть никуда не передаётся. В
трее кнопка «Новый ключ» кладёт ключ в поле и копирует в буфер строку
для сервера. Без трея:

```
go run ./cmd/genkey -name "me"
```

Строку с `public_key` отправь администратору сервера, `client_key`
оставь себе. Строка с публичным ключом для уже существующего
`client_key`: `go run ./cmd/genkey -name me -pub <client_key>`.

### 2. Сервер

Нужен Linux с Docker. На хосте один раз:

```bash
sudo sysctl -w net.ipv4.ip_forward=1
echo 'net.ipv4.ip_forward=1' | sudo tee /etc/sysctl.d/99-dormtun.conf
sudo modprobe tcp_bbr
```

В папке проекта:

```bash
cp server-config.example.json server-config.json
cp authorized_keys.example.json authorized_keys.json   # вписать public_key клиентов
go run ./cmd/gencert                                    # один раз; без Go: docker run --rm -v "$PWD":/src -w /src golang:1.27-alpine go run ./cmd/gencert
docker compose up --build -d
docker compose logs -f
```

Сертификат в образ не запекается. Он лежит в `devcerts/`, монтируется
в контейнер и переживает пересборку, поэтому пины клиентов не ломаются.
`gencert` не перезапишет существующий сертификат без `-force`. Для
сертификата на своё имя есть `-host vpn.example.com`. `server-config.json`,
`authorized_keys.json` и `devcerts/` должны существовать до первого
запуска, иначе Docker создаст на их месте пустые папки. Свежий клон:
сначала сохрани эти три вещи.

В логе должны быть `client authentication enabled`, строки `... channel
listening on ...` и `cert fingerprint ...` (отпечаток для `server_pin`).
Открой порты в firewall VPS (`ufw allow 587/tcp`). Без
`authorized_keys_file` сервер не запускается: иначе это открытый прокси.

### 3. Клиент (Windows)

```powershell
go build -o client.exe .\cmd\client
go build -ldflags "-H=windowsgui" -o tray.exe .\cmd\tray
```

Положи `tray.exe`, `client.exe` и `wintun.dll` в папку внутри Program
Files. Трей работает от администратора и запускает `client.exe` и
`wintun.dll` из своей папки. Если в неё может писать обычный
пользователь, любая программа подменит эти файлы и получит права
администратора. Вне Program Files трей предупредит один раз.

`wintun.dll` в репозитории: версия 0.14.1 с https://www.wintun.net/,
подпись WireGuard LLC, SHA-256
`E5DA8447DC2C320EDC0FC52FA01885C103DE8C118481F683643CACC3220DAFCE`.

В трее: название, адрес сервера (`IP:587`), ключ, игры (необязательно),
«Подключиться». При первом подключении клиент запоминает сертификат
сервера в `known_server.pin` и дальше сверяется с ним. Ключи в
`connections.json` зашифрованы DPAPI под текущим пользователем, в
`client-config.json` ключ не пишется: трей передаёт его `client.exe`
через переменную окружения `SPLICERTC_CLIENT_KEY`.

Без трея: `client-config.example.json` → `client-config.json`, вписать
`vpn_addr` и `client_key`, затем `.\run-vpn.ps1` из Administrator-шелла.
Если этот конфиг уже записал трей, ключа в нём нет: задай
`SPLICERTC_CLIENT_KEY` или держи для консоли отдельный конфиг
(`.\run-vpn.ps1 -Config other.json`). Настоящий шлюз скрипт ищет как
default-маршрут с наименьшей метрикой мимо TUN, поэтому другой
включённый VPN может его перехватить.

## Игровой трафик

```json
"glue_addr": "<SERVER_IP>:993",
"game_processes": ["deadlock.exe"],
"game_paths": 3
```

Клиент спрашивает у Windows (`GetExtendedUdpTable`), какой процесс
владеет UDP-портом, и UDP этих процессов отправляет через glue. TCP игры
и весь остальной трафик идут через `vpn`. Имя нужно точное, с `.exe`: в
Диспетчере задач на вкладке «Подробности» или `Get-Process -Name
"*deadlock*" | Select Path`.

Решение «glue или vpn» принимается один раз на поток и не меняется:
переезд между каналами меняет внешний адрес, и игровой сервер видит
нового клиента. Пока владелец порта неизвестен, пакеты этого потока
отбрасываются. Если владелец не нашёлся за секунду, поток идёт через vpn.
На сервере при первом пакете игры появится `glue: new flow ...`.

Поможет ли мультипас в конкретной сети, проверяется замером. Режим `tun`
с `tun_measure: true` раз в 5 секунд печатает RTT, джиттер и потери.
Сравни `tun_paths: 1` и `3` в часы пик. Все пути идут через один канал
общежития, и потери на них могут быть коррелированы.

## Задержка под нагрузкой и обрывы

Чтобы загрузки не раздували пинг:

- FQ-CoDel в туннеле на обеих сторонах;
- `TCP_NOTSENT_LOWAT` 16 КБ и BBR на сокетах сервера (лог `transport: tunnel
  sockets use BBR`; если BBR нет, выполни `sudo modprobe tcp_bbr`);
- пакетная запись: несколько кадров уходят одной TLS-записью.

Если пинг всё равно растёт при загрузке, очередь копится в роутере
сети. Поставь `vpn_down_mbps` (сервер) и `vpn_up_mbps` (клиент) на 85–90%
от реальной скорости канала.

Обрывы клиент переживает сам. vpn-канал шлёт keepalive раз в 2 с, после
7 с тишины переподключается с паузой 0.5→5 с, а TUN и маршруты остаются.
Каждый glue-путь пингуется раз в 200 мс; путь без ответа за 1 с
передозванивается, остальные работают. Неверный ключ или сменившийся
сертификат завершают клиент сразу: повторы тут не помогут, а с неверным
ключом только приведут к бану. Трей это различает и предлагает сбросить
пин, если сертификат пересоздавали на сервере.

## Безопасность

**Сервер проверяется пином.** Есть два варианта: `pin_file`, где
отпечаток запоминается при первом подключении (как `known_hosts`), и
`server_pin`, где ты сам вписываешь отпечаток из лога сервера. С
сертификатом от CA (Let's Encrypt) пин не нужен, достаточно
`server_name`. `insecure: true` без пина не проверяет ничего: это только
для тестов, клиент пишет предупреждение.

**Клиент проверяется ключом.** Подпись привязана к TLS-сессии (exporter),
поэтому её нельзя переиграть или переслать через перехватчик. Сервер
отвечает байтом «принят», и клиент с неверным ключом сразу это видит.
Три неверных ключа подряд с одного IP дают бан на 10 минут. IPv6
банится по /64. IP, с которого за последние сутки был успешный вход
(общий NAT общежития), не банится.

**Куда сервер ходит за клиента** (`internal/egress` и iptables vpn-канала):

- запрещено: loopback, link-local (метаданные облака), multicast;
- запрещено: собственные адреса сервера, включая публичный IP. В облаках
  с 1:1 NAT (AWS, GCP, Yandex Cloud) публичного IP на интерфейсе нет,
  его надо вписать в `public_ips`;
- запрещено: частные сети `10/8`, `172.16/12`, `192.168/16`, `100.64/10`
  (если не включён `allow_private_destinations`) и TCP-порт 25;
- glue не шлёт UDP на порты-усилители (DNS, NTP, SSDP, memcached и др.);
- в vpn-канал пропускаются только пакеты с адресом источника клиента,
  к клиенту — только ответы на его соединения (conntrack);
- правила iptables обязательны: если хоть одно не встало, vpn-канал не
  поднимается. Бэкенд (legacy или nft) определяется по правилам хоста.

**Ресурсы.** Рукопожатие ограничено 15 с. Лимиты: 512 UDP-потоков на
сессию, 4 сессии на клиента, 4096 потоков на сервер, 256 smux-стримов на
соединение. Логи Docker — 3 файла по 10 МБ. Адреса сайтов и игровых
серверов в лог не пишутся.

**IPv6 и DNS.** Туннель только IPv4. На время подключения правило
брандмауэра блокирует глобальный IPv6, и приложения переходят на IPv4.
TUN получает метрику 1, поэтому DNS-запросы сначала идут на 1.1.1.1
через туннель. Полностью исключить запросы к DNS общежития Windows не
даёт.

## Ограничения

- Один vpn-клиент на сервер: у TUN один адрес клиента. Переподключение
  с тем же ключом заменяет старое соединение, другой ключ получает отказ.
  Поэтому у каждого устройства должен быть свой ключ.
- Обычный трафик в vpn идёт TCP поверх TCP, со всеми вытекающими при
  потерях. Игры от этого защищены через glue.
- Для DPI туннель заметен: стандартный TLS-отпечаток Go, самоподписанный
  сертификат, TLS сразу на порту 587 без SMTP-баннера.

## Другие режимы клиента

- **`socks5`**: локальный SOCKS5 на `127.0.0.1:1080`, через reliable-канал.
  Только TCP CONNECT, прав администратора не нужно, переподключается сам.
- **`tun`**: весь UDP из TUN через glue, с `tun_paths` путями и замерами
  `tun_measure`. Маршрут на игровой сервер ставится вручную (`route add
  <GAME_IP> mask 255.255.255.255 <tun ip>`). Сам сервер туннеля через TUN
  не заворачивай: получится петля.
- **`droptest`**: синтетические кадры в droppable-канал. На сервере нужно
  включить `drop_addr`, потери вносятся через `tc netem`.

## Диагностика

`portprobe` проверяет, какие порты пропускает сеть. Сервер отвечает
токеном с номером порта, так что прозрачный прокси не выдаст себя за
открытый порт.

```bash
./portprobe -mode server -tcp 1-999 -udp none                        # на VPS, на время теста
.\portprobe.exe -mode client -host <SERVER_IP> -tcp 1-999 -udp none   # из сети общежития
```

`-sustain 5m` держит открытые порты под трафиком, `-targets default`
проверяет публичные сервисы без своего сервера. `tunprobe -name
dormtun0` печатает пакеты, которые попадают в TUN.

## Справочник полей

### `server-config.json`

| Поле | По умолчанию | Что делает |
|---|---|---|
| `vpn_addr`, `glue_addr`, `addr`, `drop_addr` | `:8447`, `:8446`, `:8443`, `off` | адреса каналов vpn, glue, reliable, droppable; `"off"` выключает канал. Без vpn не нужны TUN, iptables и `NET_ADMIN` |
| `authorized_keys_file` | — | список ключей клиентов, обязателен |
| `cert`, `key` | `devcerts/dev.crt`, `devcerts/dev.key` | сертификат TLS |
| `vpn_subnet` | `10.66.0.0/24` | подсеть vpn: сервер `.1`, клиент `.2` |
| `vpn_tun_name`, `vpn_tun_mtu` | `dormvpn0`, `1400` | TUN на сервере |
| `egress_iface` | автоопределение | интерфейс для MASQUERADE |
| `public_ips` | — | публичные IP сервера, которых нет на интерфейсах (1:1 NAT) |
| `allow_private_destinations` | `false` | пустить клиентов в частные сети за VPS |
| `vpn_down_mbps` | `0` | ограничение скорости сервер→клиент, Мбит/с |

Флаг `-allow-unauthenticated` (только командная строка) запускает
сервер без ключей для локального теста.

### `client-config.json`

| Поле | По умолчанию | Что делает |
|---|---|---|
| `mode` | `socks5` | `vpn`, `tun`, `socks5`, `droptest` |
| `vpn_addr`, `glue_addr`, `server`, `drop_addr` | localhost | адреса каналов. Имя хоста резолвится один раз, все каналы идут на один IP |
| `client_key`, `client_key_file` | — | ключ клиента, обязателен. Переменная `SPLICERTC_CLIENT_KEY` важнее обоих |
| `pin_file`, `server_pin` | — | пин сервера: файл TOFU или отпечаток вручную |
| `server_name` | хост из адреса | SNI и имя для проверки CA-сертификата |
| `insecure` | `false` | без пина не проверять сертификат, только тесты |
| `vpn_tun_name`, `vpn_tun_mtu` | `dormvpn0`, `1400` | TUN клиента |
| `vpn_subnet` | `10.66.0.0/24` | должна совпадать с сервером |
| `game_processes`, `game_paths` | —, `3` | exe игр для glue и число путей |
| `vpn_up_mbps` | `0` | ограничение скорости клиент→сервер, Мбит/с |
| `listen` | `127.0.0.1:1080` | порт SOCKS5 (`socks5`) |
| `tun_name`, `tun_mtu`, `tun_paths`, `tun_measure`, `tun_measure_interval` | `dormtun0`, `1420`, `1`, `false`, `33ms` | режим `tun` |
| `drop_count`, `drop_interval`, `drop_paths` | `0`, `33ms`, `1` | режим `droptest` |

Неизвестное поле в любом конфиге даёт ошибку при запуске: опечатка не
должна молча оставлять значение по умолчанию. Флаги командной строки с
теми же именами переопределяют поля конфига. Реальные конфиги и ключи
в `.gitignore`, в репозитории только `*.example.json`.
