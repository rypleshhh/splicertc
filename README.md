# splicertc

TCP/TLS-туннель, написанный с нуля, который прокидывает трафик через
сеть, блокирующую нестандартные порты. Два способа использования:
полноценный VPN (`vpn`-режим, весь IP-трафик) и специализированный
канал для игрового UDP с droppable-логикой и мультипас-дублированием,
чтобы минимизировать издержки по задержке/потерям при прогоне датаграмм
поверх TCP (`tun`-режим).

## Компоненты

- **server** (`cmd/server`) — работает на VPS. Каналы: reliable (в
  стиле SOCKS5, `:8443`), droppable (кадрированный, TTL-дроп, `:8444`),
  glue (реальный захваченный UDP с TUN, `:8446`), vpn (полный IP-туннель
  с NAT на сервере, `:8447` по умолчанию — на практике обычно
  переносится на порт, реально проходящий через фильтрацию сети, см.
  "Быстрый старт").
- **client** (`cmd/client`) — работает на игровой/рабочей машине.
  Режимы: `vpn` (весь трафик через туннель, опционально с селективным
  мультипасом для игр), `socks5` (локальный прокси), `tun` (захват
  игрового UDP, опционально мультипас), `droptest` (синтетическое
  тестирование потерь).
- **gencert** (`cmd/gencert`) — одноразовые самоподписанные dev-сертификаты.
- **genkey** (`cmd/genkey`) — генерация Ed25519-ключа для аутентификации
  клиента (см. "Аутентификация" ниже).
- **tray** (`cmd/tray`) — минимальное Windows-приложение поверх
  `vpn`-режима: окно редактирования конфига + иконка в трее (см.
  "Windows-приложение" ниже).
- **tunprobe** (`cmd/tunprobe`) — диагностика: показывает, что видит TUN.
- **portprobe** (`cmd/portprobe`) — диагностика сети: какие порты вообще
  проходят через фильтрацию, до и независимо от туннеля (см. "Подбор
  порта" ниже).

Всё управляется **конфиг-файлами** — `server-config.json` на сервере,
`client-config.json` на клиенте. Флаги командной строки существуют
только как разовое переопределение одного значения, не как основной
способ запуска.

## Быстрый старт

### 1. Ключ

```
go run ./cmd/genkey -name "me"
```

Выведет две строки: `public_key` (для сервера) и `client_key` (для
клиента) — это пара Ed25519-ключей, не общий пароль. Публичная часть не
секретна, приватную никому не показывай, кроме того клиента, для
которого она сгенерирована. Хочешь дать доступ другу — прогони команду
ещё раз с его именем (`-name friend1`) и получишь для него отдельную
пару; отозвать доступ одному человеку потом — удалить одну его строку
из `authorized_keys.json` на сервере, никому больше ничего менять не
нужно. Подробнее — раздел "Аутентификация" ниже.

### 2. Сервер

```
cp server-config.example.json server-config.json
cp authorized_keys.example.json authorized_keys.json
```

Сертификат — сгенерировать один раз (локально, где уже есть Go для
сборки `client.exe`) и закинуть на сервер, в ту же папку, что и
`docker-compose.yml`:
```
go run ./cmd/gencert
scp -r devcerts root@<SERVER_IP>:~/splicertc/
```

В `authorized_keys.json` впиши `public_key` из шага 1 (по одной записи
на каждого, кому даёшь доступ). `server-config.json` можно не трогать —
пример уже настроен на порт `587` для `vpn_addr` — рабочий порт для
типичной сети с фильтрацией (см. следующий раздел, если хочешь
проверить/выбрать другой), не конфликтует с 443, на котором часто уже
висит другой сервис (например, Xray). Подсеть `10.66.0.0/24` можно не
трогать. Открой порт в firewall VPS, если он есть (`ufw allow
587/tcp`) — иначе сервер поднимется, но снаружи будет недоступен.
Дальше:

```
docker compose up --build -d
docker compose logs -f
```

`docker-compose.yml` сам монтирует `server-config.json`,
`authorized_keys.json` и `devcerts/` в контейнер и запускает бинарник
вообще без флагов — весь запуск это отредактировать файлы и поднять
контейнер. Все три должны существовать ДО первого запуска (иначе Docker
создаст на их месте пустые директории вместо монтирования файлов —
команды выше как раз для этого). Монтирование `devcerts/` — не
формальность: без него каждая пересборка образа печёт новый
сертификат, и придётся заново лазить в `docker compose logs` за новым
отпечатком для всех клиентов; `go run ./cmd/gencert` делается один раз
и не трогается больше никогда (см. "Аутентификация" ниже про
`pin_file`, где это особенно важно).

Нужен Linux-хост с включённым `net.ipv4.ip_forward` (один раз, на самом
хосте, не в контейнере):

```
sudo sysctl -w net.ipv4.ip_forward=1
echo 'net.ipv4.ip_forward=1' | sudo tee /etc/sysctl.d/99-dormtun.conf
```

### 3. Клиент

```
cp client-config.example.json client-config.json
```

Открой `client-config.json`, впиши `vpn_addr` (IP твоего сервера, порт
`587`, как в примере сервера) и `client_key` из шага 1 (та же пара, чей
`public_key` уже в `authorized_keys.json` сервера). Поле `pin_file` в
примере уже настроено — при первом подключении клиент сам запомнит
сертификат сервера и будет сверяться с ним дальше, лазить в
`docker compose logs` за отпечатком не нужно (подробнее в
"Аутентификация"). Нужен `wintun.dll`
рядом с `client.exe` (https://www.wintun.net/, уже лежит в репозитории)
и **Administrator**-шелл.

Самый удобный способ запуска — `cmd/tray` (см. "Windows-приложение"
ниже): иконка в трее, "Подключиться"/"Отключиться" мышкой, без консоли
и без ручных скриптов.

Способ без GUI, но тоже одной командой — скрипт, который сам собирает
клиент, поднимает его и настраивает маршрутизацию в одном окне:

```powershell
.\run-vpn.ps1
```

Он: соберёт `client.exe`, погасит зависший процесс от предыдущего
запуска (если был), запустит клиент в этом же окне (лог виден сразу),
дождётся поднятия TUN-интерфейса и сам пропишет маршруты — включая
проверку через ipify, что трафик реально пошёл через туннель. `Ctrl+C`
— остановить. Флаги: `-Config путь.json` (другой конфиг), `-NoBuild`
(пропустить пересборку).

Ручной способ (два окна, если нужен больший контроль — что именно
делает `run-vpn.ps1` под капотом, см. "Режим vpn" ниже):
```
go build -o client.exe .\cmd\client
.\client.exe
```

### Разовое переопределение флагом

Любое поле конфига можно перебить флагом с тем же именем на один
запуск, не редактируя файл:

```
.\client.exe -mode socks5 -listen 127.0.0.1:1080
```

Имена флагов совпадают с полями конфига (см. таблицы ниже). Свой путь к
конфигу — `-config путь/к/файлу.json`.

## Подбор порта: `cmd/portprobe`

Сети с фильтрацией трафика обычно пропускают только небольшой набор
стандартных портов, и со временем этот набор может меняться — не стоит
полагаться на то, что порт 587 (или любой другой) будет работать вечно.
`portprobe` — отдельный диагностический инструмент: сервер слушает
пачку TCP/UDP-портов сразу и отвечает токеном с номером порта (чтобы
отличить "порт реально открыт" от "что-то стороннее ответило вместо
нас" — например, прозрачный прокси); клиент простукивает список и
печатает, что прошло.

Собрать (кросс-компиляция под Linux для VPS делается прямо на Windows):
```powershell
go build -o portprobe.exe .\cmd\portprobe
$env:GOOS="linux"; $env:GOARCH="amd64"
go build -o portprobe-linux .\cmd\portprobe
$env:GOOS=""; $env:GOARCH=""
```

**На VPS** (в foreground — не оставляй фоном на проде, это диагностика,
не сервис):
```bash
scp portprobe-linux root@<SERVER_IP>:~/portprobe   # с Windows
chmod +x portprobe
./portprobe -mode server -tcp 1-999 -udp none
```
Диапазоны портов задаются как `1-999` или списком `80,443,993`. Сервер
сам пропускает уже занятые порты (например, 22 у sshd, 443 у Xray) —
никогда не отнимает порт у живого сервиса. Firewall под тестируемые
порты нужно открыть отдельно (`ufw allow ...`) — иначе меряешь
собственный firewall, а не сеть.

**С клиента** (из сети, которую тестируешь):
```powershell
.\portprobe.exe -mode client -host <SERVER_IP> -tcp 1-999 -udp none -parallel 200 -timeout 2s
```

Дополнительно:
- `-sustain 5m` — после скана удержать каждый открывшийся порт 5 минут
  под трафиком: соединиться недолго и сразу отвалиться — бесполезно для
  туннеля, а `portprobe` это отдельно проверяет.
- `-targets default` (или свой список `host:port,host:port`) — проверить
  доступность известных публичных сервисов (Google, GitHub, Gmail SMTP
  и т.д.) **вообще без своего сервера и без изменений в его firewall** —
  быстрый способ понять, какие порты в принципе не заблокированы сетью,
  прежде чем открывать что-либо на своём VPS.

## Справочник: поля конфига

### `server-config.json`

| Поле | Флаг | По умолчанию | Что делает |
|---|---|---|---|
| `addr` | `-addr` | `:8443` | адрес reliable-канала (SOCKS5-стиль) |
| `drop_addr` | `-drop-addr` | `:8444` | адрес droppable-канала |
| `glue_addr` | `-glue-addr` | `:8446` | адрес glue-канала (реальный UDP) |
| `vpn_addr` | `-vpn-addr` | `:8447` | адрес full-tunnel VPN-канала |
| `vpn_tun_name` | `-vpn-tun-name` | `dormvpn0` | имя TUN-интерфейса на сервере |
| `vpn_tun_mtu` | `-vpn-tun-mtu` | `1400` | MTU серверного TUN |
| `vpn_subnet` | `-vpn-subnet` | `10.66.0.0/24` | приватная подсеть VPN (сервер = `.1`, клиент = `.2`) |
| `egress_iface` | `-egress-iface` | автоопределение | интерфейс для MASQUERADE-выхода в интернет |
| `cert` / `key` | `-cert` / `-key` | `devcerts/dev.crt` / `dev.key` | TLS-сертификат |
| `authorized_keys_file` | `-authorized-keys-file` | пусто (auth выключена) | путь к `authorized_keys.json` — список публичных ключей, которым разрешено подключаться |

### `client-config.json`

| Поле | Флаг | По умолчанию | Что делает |
|---|---|---|---|
| `mode` | `-mode` | `socks5` | `socks5` \| `droptest` \| `tun` \| `vpn` |
| `listen` | `-listen` | `127.0.0.1:1080` | локальный SOCKS5-порт (`socks5`) |
| `server` | `-server` | `127.0.0.1:8443` | адрес reliable-канала (`socks5`) |
| `drop_addr` | `-drop-addr` | `127.0.0.1:8444` | адрес droppable-канала (`droptest`) |
| `glue_addr` | `-glue-addr` | `127.0.0.1:8446` | адрес glue-канала (`tun`) |
| `tun_name` | `-tun-name` | `dormtun0` | имя TUN-интерфейса (`tun`) |
| `tun_mtu` | `-tun-mtu` | `1420` | MTU TUN (`tun`) |
| `tun_paths` | `-tun-paths` | `1` | число параллельных путей / мультипас (`tun`) |
| `tun_measure` | `-tun-measure` | `false` | слать измерительные пинги (`tun`) |
| `tun_measure_interval` | `-tun-measure-interval` | `33ms` | интервал пингов (`tun`) |
| `vpn_addr` | `-vpn-addr` | `127.0.0.1:8447` | адрес vpn-канала (`vpn`) |
| `vpn_tun_name` | `-vpn-tun-name` | `dormvpn0` | имя TUN-интерфейса (`vpn`) |
| `vpn_tun_mtu` | `-vpn-tun-mtu` | `1400` | MTU TUN (`vpn`) |
| `game_processes` | `-game-processes` | пусто | список exe (через запятую) — UDP-трафик этих процессов идёт через glue+мультипас вместо одного `vpn`-потока (`vpn`) |
| `game_paths` | `-game-paths` | `3`, если задан `game_processes` | число параллельных путей для игрового UDP (`vpn`) |
| `drop_count` | `-drop-count` | `0` | число кадров в стресс-тесте (`droptest`) |
| `drop_interval` | `-drop-interval` | `33ms` | интервал между кадрами (`droptest`) |
| `drop_paths` | `-drop-paths` | `1` | число параллельных путей (`droptest`) |
| `insecure` | `-insecure` | `false` | не проверять TLS-сертификат сервера |
| `server_pin` | `-server-pin` | пусто | SHA-256 (hex) сертификата сервера — если задан, сервер обязан предъявить именно этот сертификат |
| `pin_file` | `-pin-file` | пусто | путь к файлу для автосохранения пина при первом подключении (trust-on-first-use), альтернатива ручному `server_pin` — игнорируется, если `server_pin` задан |
| `client_key_file` | `-client-key-file` | пусто | путь к файлу с приватным ключом (`client_key` из `cmd/genkey`) — обязателен, если у сервера включена аутентификация |
| `client_key` | — | пусто | тот же приватный ключ прямо в конфиге, вместо `client_key_file` |

`server-config.json`/`client-config.json`/`authorized_keys.json` в
`.gitignore` — никогда не коммить настоящие файлы с живым ключом, в
репозитории только `*.example.json` (с плейсхолдерами).

**Про `insecure`, `pin_file` и `server_pin`**: без пина `insecure: true`
принимает ЛЮБОЙ сертификат от кого угодно — TLS-перехватывающий
middlebox в сети может подставить свой сертификат и читать весь трафик
в открытом виде, а проверка ключа клиента это не поймает (она просто
пройдёт насквозь через перехватчика к настоящему серверу).

**Рекомендуемый способ — `pin_file`** (уже настроен в примере конфига).
При первом подключении клиент примет тот сертификат, что показал
сервер, сохранит его отпечаток в указанный файл и с этого момента будет
сверяться с ним автоматически на каждом следующем запуске — точно так
же, как `known_hosts` у SSH. Никаких логов сервера читать не надо, ни
разу — при условии, что сертификат сервера **не меняется** между
подключениями, а для этого нужен смонтированный `devcerts/` из шага 2
Быстрого старта (без него каждая пересборка образа сервера меняет
сертификат, и `pin_file` пришлось бы сбрасывать заново после каждого
`docker compose up --build`). Если сервер всё же сменит сертификат
(переустановка, ручная замена) — удали файл `pin_file`, следующий
запуск снова доверится первому подключению и пересохранит.

**Альтернатива — ручной `server_pin`**: если нужен полный контроль (не
доверять автоматически даже первому подключению), сервер печатает свой
отпечаток при старте (`cert fingerprint (put this in the client's
server_pin to enable pinning): ...`, виден в `docker compose logs`) —
скопируй эту строку в `server_pin` клиента вместо `pin_file`. Работает
так же надёжно, просто требует один ручной шаг при каждой смене
сертификата вместо нуля. Если заданы оба поля — `server_pin` в
приоритете.

В обоих случаях гарантия одна и та же: сервер обязан предъявить именно
запомненный/указанный сертификат, подделать это без приватного ключа
невозможно даже с превышением TLS 1.3.

## Режим `vpn`: весь трафик через туннель

Полноценная замена обычного интернет-подключения: клиент создаёт TUN,
захватывает ВЕСЬ IP-трафик (не только UDP), сервер пишет его в свой
собственный TUN и NAT'ит наружу через ядро Linux (iptables MASQUERADE).

`client-config.json`:
```json
{
  "mode": "vpn",
  "vpn_addr": "<SERVER_IP>:587",
  "vpn_tun_name": "dormvpn0",
  "vpn_tun_mtu": 1400,
  "insecure": true,
  "client_key": "<client_key из cmd/genkey>"
}
```

### Запуск и маршрутизация

Проще всего — `.\run-vpn.ps1` (Administrator-шелл): собирает клиент,
запускает его, дожидается поднятия TUN-интерфейса и сам прописывает
маршруты ниже, всё в одном окне. Дальнейшие шаги этого раздела — то,
что скрипт делает автоматически; нужны только если требуется больше
контроля или что-то пошло не так и чинишь руками.

Запуск клиента напрямую: `.\client.exe` (Administrator-шелл), дождаться
`connected to vpn channel ...`. Дальше — маршрутизация, во ВТОРОМ
Administrator-шелле:

```
# 1. Узнать текущий шлюз (ipconfig, поле Default Gateway) и IP сервера.

# 2. Анти-луп маршрут — ОБЯЗАТЕЛЬНО до переопределения дефолтного
#    маршрута, иначе собственное соединение клиента с сервером
#    зациклится само на себя.
route add <SERVER_IP> mask 255.255.255.255 <GATEWAY_IP> metric 1

# 3. Адрес интерфейса + публичный DNS (свой DNS общаги/сети станет
#    недоступен, как только сменится дефолтный маршрут).
netsh interface ip set address name="dormvpn0" static 10.66.0.2 255.255.255.0
netsh interface ip set dns name="dormvpn0" static 1.1.1.1

# 4. Переопределить дефолтный маршрут.
route add 0.0.0.0 mask 0.0.0.0 10.66.0.1 metric 1
```

Если `route add 0.0.0.0 ...` привязался не к тому интерфейсу (`route
print -4` покажет интерфейс `10.255.164.241` вместо `10.66.0.2`) —
пересоздай с явным индексом интерфейса:
```
$idx = (Get-NetAdapter -InterfaceAlias "dormvpn0").ifIndex
route delete 0.0.0.0 mask 0.0.0.0 10.66.0.1
route add 0.0.0.0 mask 0.0.0.0 10.66.0.1 metric 1 if $idx
```

Откат (вернуть обычный интернет):
```
route delete 0.0.0.0 mask 0.0.0.0 10.66.0.1
route delete <SERVER_IP> mask 255.255.255.255 <GATEWAY_IP>
```
и `Ctrl+C` клиента.

Проверка: `ping 1.1.1.1`, `curl https://example.com`,
`curl -UseBasicParsing https://api.ipify.org` (должен вернуть IP
сервера, не свой).

### Селективный мультипас для игр (опционально)

По умолчанию весь трафик идёт одним TCP-потоком — под всплеском мелких
пакетов (например, быстрая серия действий в игре) это подвержено
TCP head-of-line blocking: один потерянный пакет придерживает все
последующие. Чтобы конкретные процессы получили мультипас-дублирование
(несколько параллельных путей, берём кого первый доехал — тот же
механизм, что у `tun`-режима), укажи их в `game_processes`:

```json
{
  "mode": "vpn",
  "vpn_addr": "<SERVER_IP>:587",
  "glue_addr": "<SERVER_IP>:993",
  "game_processes": ["deadlock.exe"],
  "game_paths": 3,
  "client_key": "<client_key из cmd/genkey>"
}
```

Клиент сам определяет, какой процесс владеет каждым UDP-портом (через
Windows IP Helper API — `GetExtendedUdpTable`, без сторонних
зависимостей), так что не нужно гадать диапазоны IP игровых серверов.
Только UDP; TCP того же процесса и весь остальной трафик по-прежнему
идёт через единственный `vpn`-поток. Серверу для этого нужен ещё и
рабочий `glue_addr` в `server-config.json` — код на сервере не меняется,
просто оба канала должны слушать (два разных порта).

#### Как узнать точное имя процесса

Классификация идёт по имени exe-файла **с расширением** (`deadlock.exe`,
не `deadlock`), потому что клиент сверяется с реальным владельцем
UDP-сокета, а не просто ищет процесс с похожим именем — значит важно
взять имя точно, включая `.exe`.

**Через Диспетчер задач** (`Ctrl+Shift+Esc`) — вкладка "Подробности",
пока игра запущена: там сразу видно точное имя в колонке "Имя".

**Через PowerShell**, пока игра запущена — список всех процессов с
видимым окном (проще всего найти игру среди них):
```powershell
Get-Process | Where-Object { $_.MainWindowTitle -ne "" } | Select-Object ProcessName, Path
```
Или сразу по подстроке в имени, если примерно знаешь его:
```powershell
Get-Process -Name "*deadlock*" | Select-Object ProcessName, Path
```
`ProcessName` в выводе PowerShell — **без** `.exe` (сам PowerShell его
обрезает), в конфиг добавь расширение сам. `Path` показывает полный
путь — оттуда видно точное имя файла однозначно.

Проверить, что классификация реально сработала, можно по логам: пока
работает `client.exe` с заданным `game_processes`, посмотри на сервере
`docker compose logs -f` — при первом обнаруженном пакете от игры там
появится `glue: new flow ... -> ...` для соответствующего адреса, чего
не будет для остального трафика (он идёт через `vpn`-канал молча).

## Windows-приложение: `cmd/tray`

Минимальный тёмный интерфейс поверх `vpn`-режима: миниатюрное окошко со
списком именованных подключений (сервер + ключ на каждое имя) вместо
ручного редактирования JSON, плюс иконка в трее для
"Подключиться"/"Отключиться" мышкой. Ничего не переизобретает — под
капотом ровно то же самое, что делает `run-vpn.ps1` (запускает
`client.exe`, дожидается поднятия туннеля, вызывает
`setup-vpn-route.ps1`), просто через окно вместо консоли.

Собрать:
```powershell
go build -ldflags "-H=windowsgui" -o tray.exe .\cmd\tray
```
`-H=windowsgui` — чтобы при запуске не мелькала консоль.

`cmd/tray/resource.syso` уже лежит в репозитории и подхватывается
сборкой автоматически (это стандартное поведение `go build`, ничего
дополнительно указывать не нужно) — он встраивает Windows-манифест
(`cmd/tray/tray.manifest`), без которого приложение падает с `create
window: TTM_ADDTOOL failed` при старте (нужна Common Controls v6, GUI-
библиотека `lxn/walk` без манифеста её не получает). Трогать
`resource.syso` руками не надо; пересоздаётся из `tray.manifest`, если
он когда-нибудь понадобится другим, через `goversioninfo` (`go install
github.com/josephspurrier/goversioninfo/cmd/goversioninfo@latest`,
дальше `goversioninfo -manifest tray.manifest -skip-versioninfo
-o resource.syso <любой-versioninfo.json>` из `cmd/tray`).

Рядом с `tray.exe` должны лежать (тот же набор, что нужен для ручного
запуска `vpn`-режима): `client.exe`, `setup-vpn-route.ps1`, `wintun.dll`.
Ни `connections.json`, ни `client-config.json` создавать заранее не
нужно — окно само их создаст при первом "Сохранить"/"Подключиться".

Двойной клик по `tray.exe` — сам запросит права администратора (UAC),
если их ещё нет (нужны для TUN-адаптера и маршрутов). Дальше:

- **Список подключений** — сверху окна: одна строка на каждое сохранённое
  имя (сервер), шрифт чуть крупнее остального окна, чтобы легче было
  попасть кликом и прочитать. Данные лежат в `connections.json` рядом
  с exe (см.
  `connections.example.json` — формат такой же простой, список объектов
  `{name, vpn_addr, client_key, game_processes}`). Двойной клик по
  строке — сразу подключиться к этому серверу. Если `connections.json`
  ещё нет, но уже есть настроенный вручную `client-config.json` (с
  прошлых версий этого приложения или из "Быстрого старта") — при первом
  запуске он сам превратится в одну запись с именем "По умолчанию", ничего
  не потеряется.
- **Поля под списком**: название, адрес сервера, приватный ключ
  (`client_key` из `cmd/genkey`, поле замаскировано точками), игровые
  процессы через запятую (необязательно, см. "Селективный мультипас для
  игр"). Клик по строке в списке подставляет её значения в поля —
  дальше можно поменять и пересохранить (в том числе переименовать —
  меняешь "Название" и жмёшь "Сохранить", старое имя не остаётся
  висеть отдельной записью). "Новое" очищает поля для новой записи.
  "Сохранить" добавляет/обновляет запись в списке и пишет её в
  `connections.json`, "Удалить" — убирает выбранную. Кнопка "Пинг"
  проверяет прямо сейчас, что сервер отвечает и ключ принят — реальное
  TLS+авторизация на `vpn_addr` с текущим `client_key` из полей (не
  просто "порт открыт"), без полного поднятия туннеля и маршрутизации;
  полезно проверить перед "Подключиться", особенно после правки полей.
  Кнопка "Подключиться" под полями сначала сохраняет, потом
  подключается — как двойной клик по строке, только с текущими
  несохранёнными правками.
- **Если списка подключений ещё нет** — окно открывается сразу; если
  хотя бы одно сохранено — приложение сворачивается прямо в трей, без
  лишнего окна на экране.
- **Трей-иконка**: серая — отключено, зелёная — подключено, красная —
  ошибка. Правой кнопкой — меню: "Настройки" (открыть/поднять то же
  окно в любой момент), "Подключиться" (использует то, что уже записано
  в `client-config.json` последним подключением), "Отключиться",
  "Открыть журнал" (открывает `tray.log` рядом с exe — туда пишется
  вообще всё: вывод `client.exe`, вывод скрипта маршрутизации, статусы),
  "Выход". Крестик на самом окне просто прячет его обратно в трей —
  по-настоящему закрывает приложение только "Выход".
- **Тёмная тема** — заголовок окна и все поля/кнопки/список в тёмных
  цветах (через `DwmSetWindowAttribute`/`SetWindowTheme`, тот же приём,
  которым многие Win32-приложения красят себя в тёмное на Windows 10/11
  без полной перерисовки элементов вручную). Не настраивается и не
  следует за системной темой — просто всегда тёмное.

**Честно про ограничения**: это тонкая обёртка, а не переписанный с
нуля более надёжный клиент. Если туннель оборвётся сам по себе
(`client.exe` всё ещё падает на любом разрыве соединения — см. IDEAS.md
P1 #4, это не пофикшено), приложение это заметит и покажет "клиент
неожиданно завершился", но не переподключится сам — нужно нажать
"Подключиться" заново. Считай это удобной панелью управления поверх
существующего стека, а не гарантией автоматического реконнекта.

## Аутентификация

Без `authorized_keys_file` в конфиге сервер принимает подключения от
кого угодно, кто найдёт его IP:порт — открытый прокси и открытый
UDP/IP-релей.

Аутентификация — по Ed25519-ключам, а не по общему паролю: у сервера
список публичных ключей (`authorized_keys.json`, одна запись на
человека), у каждого клиента свой приватный ключ. Так можно отличить
одного друга от другого в логах и отозвать доступ одному, не трогая
остальных — удалить его строку из `authorized_keys.json` и
перезапустить сервер.

Сгенерировать пару (один раз на каждого, кому даёшь доступ, включая
себя самого):
```
go run ./cmd/genkey -name "friend1"
```
Выведет `public_key` (вставить строкой в `authorized_keys.json`
сервера) и `client_key` (вставить в `client_key` того человека,
клиент-конфиг). Публичный ключ не секретен — его можно передать хоть в
открытом чате. Приватный (`client_key`) — секрет ровно как раньше был
`psk`: передавай по каналу, которому доверяешь, никогда не коммить в
git (`client-config.json` и `authorized_keys.json` уже в `.gitignore`,
в репозитории только `*.example.json`).

У приватного ключа нет отдельного флага командной строки (только
`-client-key-file <путь>`) специально для этого: командная строка видна
любому локальному пользователю через `/proc/<pid>/cmdline` — храни
ключ только в конфиге (`client_key`) или отдельном файле
(`client_key_file`).

**Защита от подбора/сканирования**: после 3 неудачных попыток
аутентификации (неверный публичный ключ, битая подпись и т.п.) с одного
IP сервер банит этот IP на 10 минут — новые подключения с него
отклоняются сразу, без попытки хендшейка. Успешная аутентификация
сбрасывает счётчик. Бан ничем не отличает сканер от легитимного
клиента, который просто опечатался в своём `client_key` — поэтому срок
короткий, а каждый бан громко логируется (`auth: banning <IP> until
...`), так что если свой же клиент вдруг перестал подключаться, причина
сразу видна в `docker compose logs`.

Glue-канал дополнительно отказывается релеить на loopback, link-local и
multicast-адреса и на горстку UDP-портов, характерных для
amplification-атак (DNS, NTP, memcached, SSDP и т.д.), независимо от
того, кто просит — защита в глубину даже на случай ошибки
аутентифицированного клиента.

## Первый запуск: dev-сертификаты

```
go run ./cmd/gencert
```

Создаёт `devcerts/dev.crt`/`dev.key` — одноразовую самоподписанную пару
для localhost (дефолт `cert`/`key` в конфиге сервера указывает сюда).
`insecure: true` на клиенте пропускает проверку этого сертификата —
годится для личного туннеля к серверу, которым владеешь по IP, не
замена настоящему pinning'у.

## Режим `socks5`: локальный прокси

Исходный режим проекта: клиент поднимает локальный SOCKS5-прокси,
сервер форвардит то, что через него просят открыть. TCP-only (нет SOCKS5
UDP ASSOCIATE) — не годится для игр, зато не требует Administrator/TUN.

`client-config.json`:
```json
{
  "mode": "socks5",
  "listen": "127.0.0.1:1080",
  "server": "<SERVER_IP>:8443",
  "insecure": true,
  "client_key": "<client_key из cmd/genkey>"
}
```

```
.\client.exe
```

Направь любое SOCKS5-совместимое приложение (браузер, curl и т.д.) на
`127.0.0.1:1080`.

## Режим `tun`: игровой UDP, измерение и мультипас

Захватывает только реальный UDP-трафик (не общий интернет) через glue-
канал, с опциональным дублированием по нескольким путям.

`client-config.json`:
```json
{
  "mode": "tun",
  "glue_addr": "<SERVER_IP>:8446",
  "tun_name": "dormtun0",
  "tun_mtu": 1420,
  "tun_paths": 1,
  "tun_measure": true,
  "tun_measure_interval": "33ms",
  "insecure": true,
  "client_key": "<client_key из cmd/genkey>"
}
```

`.\client.exe` — даёт скользящую сводку каждые 5 секунд: RTT
(min/mean/p95/max), джиттер, потери, только для плеча клиент<->сервер.
Дай поработать 30+ секунд, `Ctrl+C`, поменяй `tun_paths` на `3` в
конфиге, перезапусти — та же сеть, тот же сервер, сравнение loss/jitter
между двумя прогонами и есть ответ на вопрос "помогает ли мультипас на
моей реальной связи". Маршрут через TUN и игра не нужны — пинги
генерирует сам клиент.

Чтобы реально завернуть игровой сервер через TUN (не только измерять):
```
netsh interface ip set address name="dormtun0" static 10.99.0.1 255.255.255.0
route add <GAME_SERVER_IP> mask 255.255.255.255 10.99.0.1
```

**Не заворачивай через TUN сам сервер туннеля** (`route add
<SERVER_IP> ... dormtun0`) — собственное соединение клиента с сервером
уйдёт в тот же TUN, который оно обслуживает, — петля. Только реальные
адреса игровых серверов.

## Диагностика того, что видит TUN-интерфейс

`tunprobe` — отдельный бинарник, без туннеля вообще, конфига не
использует (разовая диагностика — флаги тут уместнее):

```
go build -o tunprobe.exe ./cmd/tunprobe
.\tunprobe.exe -name dormtun0 -mtu 1420
```

Показывает, что идёт и как классифицируется (реальный трафик vs.
локальный шум вроде mDNS/SSDP/NetBIOS) — полезно проверить перед тем,
как подключать интерфейс к чему-либо.

## Тестирование поведения при потерях (Linux, игра не нужна)

`droptest` шлёт синтетические кадры; сочетай с `tc netem` на loopback
сервера, чтобы вносить реальные потери.

`client-config.json`:
```json
{
  "mode": "droptest",
  "drop_addr": "<SERVER_IP>:8444",
  "drop_count": 300,
  "drop_interval": "33ms",
  "drop_paths": 3,
  "insecure": true,
  "client_key": "<client_key из cmd/genkey>"
}
```

```
sudo tc qdisc add dev lo root netem loss 20% delay 40ms 15ms
./client
sudo tc qdisc del dev lo root
```

`insecure: true` пропускает проверку TLS-сертификата — только для
разработки/тестирования.
